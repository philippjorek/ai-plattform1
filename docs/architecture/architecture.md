# Architecture

This documents the **current, actual** setup of this repo, as observed in the
code — not the aspirational target. Where the code and `CLAUDE.md` disagree
with what's actually wired up and running, that's called out explicitly below.

## Big picture

This is a **client-side React SPA** (Vite + React 19 + TanStack Router),
served as a static bundle, plus **two small standalone Node HTTP APIs**
(`server/formular-server.mjs`, `server/chat-server.mjs`) that the SPA talks to
over `fetch`. There is no server-side rendering in production, despite
`@tanstack/react-start` being a dependency and SSR-shaped scaffolding
(`src/start.ts`, `src/server.ts`) existing in the tree — see
[SSR scaffolding is present but dormant](#ssr-scaffolding-is-present-but-dormant).

```
Browser
  │
  ├─ GET /            → static SPA bundle (index.html + JS/CSS), client-side routed
  ├─ POST /api/formular       → formular-server.mjs (port 8090) → data/formular-submissions.json
  ├─ POST /api/chat           → chat-server.mjs (port 8091)     → Open WebUI (OpenAI-compatible API)
  └─ POST /api/chat-feedback  → chat-server.mjs (port 8091)     → data/chat-feedback.json
```

## Frontend

- **Entry point**: `index.html` loads `src/main.tsx` directly (a plain Vite
  SPA entry) — this is the actual entry used by the build, not
  `src/router.tsx`'s `getRouter()`. `main.tsx` builds its own `QueryClient`
  and `createRouter()` call inline and duplicates what `router.tsx` does;
  `router.tsx`'s `getRouter` export is currently unused by the entry.
- **Routing**: `@tanstack/react-router` file-based routing, routes in
  `src/routes/`. `src/routeTree.gen.ts` is generated by the
  `@tanstack/router-plugin` Vite plugin — never hand-edited. See
  `src/routes/README.md` for the file → URL convention table.
- **App shell**: `src/routes/__root.tsx` defines the single root route —
  global `<head>` meta/fonts (`styles.css`, `fonts.css`), a
  `QueryClientProvider`, the app-wide `notFoundComponent`/`errorComponent`,
  and mounts `<ChatWidget />` outside `<Outlet />` so it's present on every
  page.
- **Page shell pattern**: pages compose `<SiteNav />` (fixed, scroll-aware
  glass header, links: Home, Architecture, Projekte, Kontakt) +
  `<ParallaxHero>` (scroll-parallax hero image from `src/assets/`) + content
  sections wrapped in `<Reveal>` (IntersectionObserver fade/slide-in) +
  `<SiteFooter />`.
- **Live pages**: `/` (`index.tsx`), `/architecture`, `/projekte`, `/kontakt`,
  `/impressum`, `/datenschutz`. `ind2.tsx` and `test.tsx` are unlinked
  scratch/legacy routes still present in `src/routes/`.
- **UI components**: `src/components/ui/` is shadcn/ui (New York style,
  Tailwind v4, `lucide-react` icons), configured via `components.json`
  (`@/components`, `@/lib`, `@/hooks`, `@/components/ui` aliases). Treat as
  generated/vendored — put app-specific components in `src/components/`
  instead of editing `ui/` internals.
- **Styling**: Tailwind v4, CSS-based theme in `src/styles.css`
  (`@theme inline` + OKLCH custom properties, "Midnight Indigo" palette).
  Custom utility classes (`glass`, `grid-bg`, `text-gradient`, `glow-ring`,
  `animate-pulse-glow`, `reveal`/`.in`) are defined there.
- **Chat widget**: `src/components/ChatWidget.tsx` is a floating chat panel
  mounted globally from `__root.tsx`. It posts message history to
  `/api/chat` and thumbs-up/down ratings to `/api/chat-feedback`, with a
  canned German fallback message if the request fails.
- **Path alias**: `@/*` → `src/*`, defined in three places that all need to
  stay in sync: `tsconfig.json` (type-checking), `components.json` (shadcn
  generation), `vite.config.ts` `resolve.alias` (actual runtime/dev-server
  resolution).

## Backend / APIs

Every endpoint is defined **once**, as an `ApiRoute` in `src/api/`, and
served two ways from that single table (`src/api/index.ts`):

- **dev/preview** — `devApiPlugin(apiRoutes)` (`src/api/vite-plugin.ts`),
  registered as a Vite plugin in `vite.config.ts`. Serves every route.
- **production** — `createApiServer(routes)` (`src/api/node-server.ts`),
  wrapped by the thin entrypoints in `server/*.mjs`, each of which owns a
  subset of the table on its own port.

| Endpoint | Route definition | Production process |
| --- | --- | --- |
| `POST /api/formular` | `src/api/formular.ts` | `server/formular-server.mjs`, port **8090** |
| `POST /api/chat` | `src/api/chat.ts` | `server/chat-server.mjs`, port **8091** |
| `POST /api/chat-feedback` | `src/api/chat-feedback.ts` | `server/chat-server.mjs`, port **8091** |
| `GET /api/vector/all` | `src/api/vector.ts` | `server/vector-server.mjs`, port **8092** |
| `GET /api/vector?id=` | `src/api/vector-fetch.ts` | `server/vector-server.mjs`, port **8092** |

Everything common to the endpoints — OPTIONS preflight, CORS headers, per-IP
rate limiting, bounded body reading, JSON writing, error-to-status mapping —
lives in `src/api/dispatch.ts` and happens once, for all routes. A route
only declares what is specific to it: path, method, size and rate limits,
its handler, and how its errors map to a response.

The only intentional difference between the two ways of serving is the
fallthrough: the Vite plugin hands an unmatched request back to the
middleware chain (so the SPA answers it), while a standalone server answers
`404 {"ok":false}`.

- `devApiPlugin` only runs inside `vite dev` / `vite preview` — there is
  **no production server wired into the Vite/Nitro build** (the `nitro`
  plugin import in `vite.config.ts` is commented out).
- `src/lib/formular-store.ts` — validates (`zod`) and appends contact-form
  submissions to `data/formular-submissions.json`.
- `src/lib/chat-feedback-store.ts` — validates and appends chat
  thumbs-up/down ratings to `data/chat-feedback.json`.
- `src/lib/chat-client.ts` — validates the chat request, prepends a German
  system prompt (references `/kontakt` and `jorek@impli.de`), and proxies to
  Open WebUI's OpenAI-compatible `/api/chat/completions` endpoint. Reads
  `OPEN_WEBUI_URL` / `OPEN_WEBUI_API_KEY` / `OPEN_WEBUI_MODEL` from the
  environment (`.env`, not committed); returns `null` from `readChatEnv()`
  if any are missing, and the caller returns 503.
- The production servers are plain `node:http` processes with **no build
  step**: they run directly via `node server/formular-server.mjs` etc. Node
  executes the imported TypeScript itself (native type stripping, which is
  on by default from **Node 22.18**), which is why every relative import in
  the `src/api/` → `src/lib/` server graph carries an explicit `.ts`
  extension — plain Node ESM does not do extensionless resolution.
- Whatever fronts the site (nginx, or the container's own process) must
  reverse-proxy the API routes to these ports.

### SSR scaffolding is present but dormant

- `src/start.ts` (`createStart` + `errorMiddleware`), `src/server.ts`
  (Cloudflare Worker-shaped `fetch` entrypoint that post-processes h3's
  swallowed-error JSON shape), and `src/lib/error-capture.ts` (global
  `error`/`unhandledrejection` listener with a 5s-TTL last-error cache) are
  built to work together as SSR error-recovery for a `@tanstack/react-start`
  server build.
- **None of this is currently in the active build path.** `index.html` /
  `main.tsx` is a plain client SPA entry, the `TanStackStartVite` and
  `nitro` Vite plugins are commented out in `vite.config.ts`, and there is
  no `wrangler.toml`/`wrangler.jsonc` anywhere in the repo despite `CLAUDE.md`
  stating the app "deploys to Cloudflare via Nitro/Wrangler." If this SSR
  path gets re-enabled, all three files need to stay in sync (see comments
  in each file) — but as of now it's unused scaffolding, not live
  infrastructure.
- `src/lib/error-reporting.ts` (`reportError`) is the one piece of this that
  *is* live: it's called from `__root.tsx`'s `errorComponent` to log
  uncaught render errors in the browser.

## Data persistence

- Flat JSON files under `data/` (`formular-submissions.json`,
  `chat-feedback.json`), read-modify-write on each request, no database.
- In the Docker production setup (`docker-entrypoint.sh`), `data/` is a
  symlink into a separate named volume mounted at `/data`, so submissions
  survive the container's git checkout being wiped and re-cloned on every
  start.

## Build & test

- `npm run dev` — `vite dev`, fixed port 8082, host `0.0.0.0`.
- `npm run build` / `build:dev` — `vite build` (production/development mode);
  output is a static client bundle (no server output, since Start/Nitro is
  disabled).
- `npm run preview` — `vite preview --port 8082`, serves the built static
  bundle; this is what production actually runs as the "web" process.
- `npm test` / `test:watch` — Vitest, jsdom environment, config in
  `vite.config.ts`'s `test` block, setup file `src/test/setup.ts`.
- `npm run lint` / `npm run typecheck` / `npm run format` — ESLint, `tsc
  --noEmit`, Prettier.

## Deployment

Production is an already-running Docker container named `aiplattform2deploy`
on the Ubuntu server, whose startup command is this repo's
`Dockerfile`/`docker-entrypoint.sh`. That script clones/pulls the repo,
`npm ci && npm run build`s it, then runs three processes in the one
container: the web preview server (port **8082**), `formular-server.mjs`
(port **8090**), and `chat-server.mjs` (port **8091**). Secrets come from
`/run/secrets/app.env` mounted read-only. If any of the three processes
dies, the whole container exits so Docker's restart policy recreates it
(picking up any newer commit on next start).

On top of that, `.github/workflows/deploy.yml` drives deploys on every push
to `main`: after `test` and `build` CI jobs pass, a **self-hosted runner on
the Ubuntu server** runs `docker exec` into `aiplattform2deploy` to
`git pull`, `npm ci`, `npm run build` (pre-warming the build before the
restart picks it up), then `docker restart`s it so `docker-entrypoint.sh`
re-runs and relaunches the three processes. `deploy.yml`'s `APP_DIR`
(`/home/www/20260709/ai-plattform2`) matches both this repo's actual
checkout location and `docs/deployment/DEPLOYMENT.md`. A reverse proxy in
front (nginx, outside this repo) routes `deploy.service-mit-herz.de` by
path: `/` → 8082, `/api/formular` → 8090, `/api/chat` and
`/api/chat-feedback` → 8091. See `DEPLOYMENT.md` for full setup.

`.github/workflows/ci.yml` runs on push/PR to `main` (Node 20 & 22 matrix):
install → lint (non-blocking) → typecheck → test → build, as pure
validation with no deployment side effects.

One leftover from an earlier project name: `Dockerfile`'s `REPO_URL`
defaults to `philippjorek/ai-plattform1.git`. In practice this doesn't bite
because `docker-entrypoint.sh` only uses `REPO_URL` to clone when
`$APP_DIR/.git` doesn't already exist — the container's checkout at
`/home/www/20260709/ai-plattform2` already exists with its own correctly
configured remote, so the entrypoint just `fetch`/`reset --hard`s it and
never consults `REPO_URL`. Worth fixing if this container is ever rebuilt
from scratch.

## Known gaps / inconsistencies worth knowing about

- `main.tsx` and `router.tsx` both construct a router/QueryClient
  independently; only `main.tsx`'s is actually used (via `index.html`).
- SSR scaffolding (`start.ts`, `server.ts`, Cloudflare Worker shape) is
  dead code under the current Vite SPA build — see above.
- `Dockerfile`'s `REPO_URL` still points at the old `ai-plattform1` repo
  name — harmless today (see [Deployment](#deployment)), but stale if the
  container is ever recreated from scratch.
- `kontakt.tsx` contact form has had multiple repair passes (see git log);
  legacy variants (`ind2.tsx`, `test.tsx`) remain in `src/routes/` unlinked
  from `SiteNav`.
