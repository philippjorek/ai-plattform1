System architecture

Service-mit-Herz

A client-side React SPA backed by two small standalone Node APIs, all three processes running inside one long-lived Docker container — not the Cloudflare/SSR shape the stack suggests.

Vite · React 19 · TanStack Router Tailwind v4 · shadcn/ui node:http · no framework Docker · GitHub Actions (self-hosted)

Request flow

There is no server-side rendering in production. The browser fetches a static SPA bundle and talks to two sibling Node processes directly over fetch for the two stateful features — the contact form and the chat widget.

Two implementations, one API surface

Each of the three POST endpoints exists twice — once as a Vite dev-server middleware plugin, once as a standalone node:http process for production — sharing validation and persistence logic from src/lib/*-store.ts.

EndpointDev / previewProduction
POST /api/formular formularApiPlugin in vite.config.ts server/formular-server.mjs · :8090
POST /api/chat chatApiPlugin in vite.config.ts server/chat-server.mjs · :8091
POST /api/chat-feedback chatFeedbackApiPlugin in vite.config.ts server/chat-server.mjs · :8091

The Vite plugins only run under vite dev / vite preview — there is no production server wired into a Nitro/Vite build; the nitro plugin import in vite.config.ts is commented out.

Deploy pipeline

Every push to main fires two independent workflows. One only validates; the other actually redeploys, ending in a docker restart that re-runs the same entrypoint shown above.

Known gaps

Documented inconsistencies worth knowing about before touching this area — none are incidents, all are pre-existing.

SSR scaffolding is dormant. src/start.ts, src/server.ts and the Cloudflare Worker-shaped error recovery exist fully wired to each other, but the TanStackStartVite and nitro Vite plugins are commented out — despite CLAUDE.md stating the app deploys to Cloudflare via Nitro/Wrangler, there is no wrangler.toml anywhere in the repo.
Duplicate router construction. Both main.tsx and router.tsx build their own QueryClient/router; only main.tsx (loaded from index.html) is actually used.
Stale REPO_URL. The Dockerfile default still points at the old ai-plattform1 repo name — harmless only because the entrypoint skips cloning whenever $APP_DIR/.git already exists.
Unlinked legacy routes. ind2.tsx and test.tsx remain in src/routes/, reachable by URL but not linked from SiteNav.
No file locking on the JSON stores. Both stores read-modify-write flat JSON files with no lock; concurrent writes race. Mitigated, not fixed, by the per-IP rate limits on both endpoints.
